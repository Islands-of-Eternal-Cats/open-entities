# Core API (WASM ↔ TypeScript)

Контракт между Rust/WASM-ядром и слоем визуализации.

**Первая установка:** если папки `wasm-bindings/pkg/` ещё нет, сначала соберите WASM:
`npm run build:wasm`, затем `npm install`.

## Общая схема

- **Ядро (WASM)** выполняется в **web worker**: симуляция, ECS-логика, состояние мира. Не знает о
  DOM и канвасе.
- **Визуализация (TS)** в главном потоке: рендер, ввод, UI. Общается с ядром через `postMessage`
  (см. `core/worker-types.ts`).

Граница — только данные и вызовы функций; никаких общих мутабельных структур.

## Как устроен обмен

Ядро отдаёт мир одним JSON: `Simulation.getWorldAsJson()`, схема версии 5 (в ней есть `tick` — номер тика снимка). Воркер разбирает его и
превращает в плоские строки `EntitySnapshot`, с которыми работает визуализация. Строки без
`entity_type` (сущности, созданные не из шаблона) и без позиции в снапшот не попадают.

**Идентификатор.** Ядро адресует сущности парой `{index, generation}`. Визуализации нужен строковый
ключ — для `Map` спрайтов и для `data`-атрибутов в DOM, — поэтому пара упаковывается в
`"<index>:<generation>"`. Обе функции лежат в `core/types.ts`: `entityIdToKey` и `keyToEntityId`.
Пара переживает despawn корректно: индекс может быть переиспользован, но поколение будет другим, и
старый ключ на новую сущность не укажет.

**Время.** Ядро идёт только целыми тиками постоянной длины: `TICK_MS` = 50 мс, `step()` — ровно
один тик, дельту хост не передаёт. Главный поток каждый кадр отправляет воркеру `frame` с реально
прошедшими миллисекундами (из `requestAnimationFrame`). Воркер (`FrameClock` в
`core/fixed-step.ts`) копит их в аккумуляторе и вызывает `step()`, пока в нём есть целый тик, но не
больше `MAX_STEPS_PER_FRAME` за кадр — лишнее после долгой паузы отбрасывается, а не догоняется.
Поэтому мир на 60 и на 144 Гц одинаков на одном и том же тике.

Ответ на `frame` приходит каждый кадр, в том числе в кадрах без шага: состояние текущего тика `t`,
позиции тика `t−1` (`previous`) и `alpha = accumulator / TICK_MS`. Если за кадр прошло несколько
шагов, `previous` — это именно тик `t−1`, а не состояние на начало кадра. Рендер рисует
`interpolate(previous, entities, alpha)`; новая сущность без позиции на `t−1` рисуется там, где
она есть. При инициализации воркер сверяет `TICK_MS` с `tickMs()` ядра.

**Приказы — это команды.** Между шагами мир не меняется никогда. Любой приказ главный поток
превращает в команду (`Command` в `wasm-types.d.ts`: `{ type: "move_to", ids, target }` и т. д.,
точки и радиусы в единицах карты) и шлёт воркеру одним сообщением `submit`. Воркер передаёт каждую
в `Simulation.submit` — команда встаёт в очередь на тик `currentTick() + 1` — и отвечает
`submitted` с номерами (`seq`). Применяется команда в начале шага, который производит этот тик;
`step()` возвращает отчёт `{ tick, outcomes }`, воркер копит outcomes всех шагов кадра и
отправляет их в ответе на `frame`. Главный поток держит `seq` → ожидающий промис и разрешает его,
когда `frame` приносит outcome с этим `seq`:

- `{ seq, ok: true, spawned | group | mission }` — для создания, с новым id;
- `{ seq, ok: true, applied, skipped }` — для остальных приказов: скольких сущностей приказ
  коснулся и сколько пропустил;
- `{ seq, ok: false, error }` — ядро отказало; промис отклоняется с этим текстом.

Ответы на приказы снапшотов не несут: мир рисуется только из `frame`. Поэтому позиции больше не
прыгают на кадр, когда ответ на приказ приходит между кадрами, — у приказа просто нет своего
снапшота. Цена — задержка до следующего тика (до 50 мс плюс кадр), то есть ровно то, что будет и в
сетевой игре: в lockstep приказ тоже исполняется на известном тике, а не в момент клика.

Немедленные методы `Simulation` (`orderMoveTo`, `orderBoard`, `createGroup`…) остаются в ядре для
инструментов и тестов, но воркер их больше не вызывает: изменение мира между шагами не попало бы ни
в реплей, ни к другим участникам сетевой игры.

## API главного потока (`core/wasm.ts`)

- **`initWasm()`** — создаёт воркер, **на главном потоке** качает `open_entities_wasm_bg.wasm`
  (с обходом кэша), `fixtures/entities.yaml` и `fixtures/init_map.yaml`, передаёт буфер и оба YAML
  воркеру. Воркер вызывает `init(wasm)`, `new Simulation()`, `loadTemplatesYaml`, `loadMapYaml`.
  Вызывать один раз до всего остального.
- **`isWasmReady()`** — `true` после успешного `initWasm()`.
- **`snapshot()`** — состояние мира без продвижения времени.
- **`frame(elapsedMs)`** — сообщает прошедшее время; воркер делает столько тиков, сколько
  помещается (возможно, ни одного), и резолвится `{ entities, previous, alpha, tick }`. Попутно
  разрешает промисы приказов, чьи outcomes пришли в этом кадре.
- **`spawnAt(typeName, x, y, faction?)`** и **`spawnRandomAt(typeName, faction?)`** — команда
  `spawn`; резолвятся новой сущностью из того кадра, в котором она появилась.
- **`moveSelectedTo(entityIds, point)`** — команда `move_to` для списка ключей из снапшота;
  резолвится outcome (`applied`/`skipped`). Пустой список — ошибка.

## Группы

- **`createGroupWith(faction, entityIds)`** — создаёт группу и заводит в неё указанные юниты,
  резолвится id группы. Два круга через ядро: у группы нет id, пока не применилась команда
  `create_group`, и только после этого уходят `add_to_group` по одной на юнит. Отказ по любому
  юниту (чужая фракция) отклоняет промис.
- **`orderGroupTo(group, point)`** — приказ всей группе. Отличие от `moveSelectedTo` не в охвате,
  а в источнике: это `GroupSteering`, и члены группы, идущие по личному приказу, его сохраняют.

В интерфейсе: кнопка «Form group» (или `G`) собирает группу из выделения, переключатель
«Group orders» решает, куда уходит клик по пустой земле — в личный приказ выделенным или в
групповой. Разница видна глазами: отдайте одному юниту личный приказ, потом уведите группу в
другую сторону — он продолжит идти своей дорогой.

## Транспорт

- **`boardUnits(entityIds, vehicleId)`** — приказ сесть в машину (`orderBoard` в ядре). Не
  телепорт: ядро вешает на юнита `BoardingTarget`, каждый тик ведёт его к текущей позиции машины
  (догоняет, если она уехала) и сажает, когда он ближе `BOARDING_RANGE`. Пока идёт — в снапшоте
  `boarding: <id машины>`, в HUD «N on the way». Пришёл, а мест нет — остаётся снаружи, приказ
  снят. **S** и новый приказ движения отменяют посадку. `reject` только если у цели нет мест
  вовсе. Команда `board`.
- **`unboardUnits(entityIds)`** — высаживает пассажиров рядом с машиной (команда `unboard`;
  кто не ехал, попадает в `skipped`).
- **`stopSelected(entityIds)`** — обнуляет скорость и снимает цель движения. Нужен именно как
  отдельный приказ: машина, продолжающая ехать после высадки, оставляет пассажиров позади, а
  больше ничто цель движения досрочно не снимает.

В снапшоте появилось и поле `moveTarget` — цель движения прямо из экспорта, в списке сил она
печатается как `→ (x, y)`. Это единственная часть состояния юнита, у которой нет вида на карте:
юнит со старой целью выглядит так же, как стоящий на месте, — ровно до момента, когда пойдёт.

В снапшоте появились ещё три поля. `seats` — число мест из компонента `Boardable`, `null` у всех,
кто не машина. `aboard` — ключ машины, в которой едет юнит, или `null`. `boarding` — ключ машины, к
которой юнит идёт садиться, или `null`. Два последних воркер добирает сам: `PassengerOf` и
`BoardingTarget` хранят сущность и в экспорт не входят, поэтому связи читаются обратно вызовами
`passengers()` и `approaching()` — по одному на машину, машин мало, зато главный поток не ходит
за этим каждый кадр.

Пассажир стоит ровно там же, где машина, поэтому на канвасе он гасится до `alpha 0.35`, а в списке
сил строка подписана `aboard <id>`; идущий на посадку — `boarding <id>`.

В груз демка берёт только то, у чего есть `velocity`: в этом движке наличие velocity и есть
подвижность, а значит и признак того, что вещь можно везти. Ядро либеральнее — ему от пассажира
нужна лишь позиция, и вопрос «считается ли самоходка грузом» решает игра, а не ECS, — но
предлагать погрузить базу в грузовик демка не будет.

В интерфейсе: выделите машину вместе с юнитами (где бы они ни стояли) и нажмите **B** (кнопка «Board»), **U** —
высадить, **S** — остановить выделенное. Выделенной машины достаточно, чтобы высадить всех, кого
она везёт.

Приказ движения пассажиру ядро отклоняет: пока он едет, цель всё равно недостижима, а после
высадки она бы сработала и увела юнита от машины. Так и выглядел баг — выделяешь грузовик вместе
с пассажиром, кликаешь по земле, а при высадке юнит уходит в свой слот сетки в пяти единицах от
машины и сесть обратно уже не может.

Высадка кладёт юнита в 1.5 единицы сбоку от машины, но машину при этом не останавливает: если
у неё остался приказ движения, она уедет, а высаженный останется. **S** — чтобы этого не было.

## Что доступно в ядре, но ещё не проброшено в интерфейс

`Simulation` умеет больше, чем использует демо: `isAlive(id)`, `mapBounds()`, `vehicleOf(id)`,
`freeSeats(id)`, `missionOf`, `isMissionCompleted`, `groupOf`, `groupMembers`, `isGroupManual`,
`schedule(tick, command)` и `stateHash()` — хэш состояния, 16 hex-цифр, одинаковый на всех
платформах. Приказы, у которых ещё нет кнопки, уже есть как команды: `despawn`, `create_mission`,
`assign_group`, `unassign_group`, `remove_from_group`, `clear_group_manual`. Наверх такой приказ
добавляется одной обёрткой в `wasm.ts` по образцу `orderGroupTo` — `order({ type: …, … })`; воркер
и протокол менять не нужно.

## Пересборка wasm в dev-режиме

`npm run dev` собирает wasm один раз на старте (`build-wasm.sh`), дальше следит плагин
`watch-rust-dirs`. Он слушает `change`, `add` и `unlink` по `.rs`, а не один `change`: git пишет
временный файл и переименовывает его поверх целевого, поэтому `git am` и смена ветки приходят как
`unlink` + `add`. Пока слушался только `change`, применение патча не запускало пересборку — в
браузере продолжало работать прежнее ядро, а исходники на диске говорили обратное.

Какая сборка в браузере — теперь написано в шапке: `Core ready (worker) · core 3f2a1c8e · 1.42 MB`.
Это FNV-1a по байтам модуля, которые реально загрузились, считается в `initWasm` до передачи
буфера воркеру. Перезагрузили страницу после пересборки, а отпечаток тот же — значит ничего не
пересобралось, и дальше искать баг в коде бессмысленно.

Если сомневаетесь, какая сборка в браузере: в консоли dev-сервера должна быть строка
`[watch-rust] Rust sources changed, rebuilding WASM...`, а после неё `WASM copied to ...`. Нет их —
жмите Ctrl+C и `npm run dev` заново.

## Семантика ввода (selection + orders)

Правила слоя визуализации:

- Move order отправляется **только** при обычном клике по пустой земле (или по миникарте), когда
  есть активный `selection`.
- Любой модификатор (`Shift`/`Ctrl`/`Alt`/`Meta`) блокирует отправку приказа.
- `Shift+click` — только операции выбора, не приказ.
- Очистка выделения выполняется явно: `Esc`, кнопка UI, либо правый клик по канвасу.
- Клик по пустоте без модификаторов при активном выделении не очищает выделение, а трактуется как
  приказ движения.

| Сценарий | Ожидаемое действие |
|------|------------|
| Обычный клик по пустой земле при активном выделении | Отправить приказ движения |
| Shift/Ctrl/Alt/Meta + клик по пустоте | Приказ не отправлять |
| Клик по миникарте с модификаторами | Только навигация камеры |
| Esc / кнопка UI / правый клик | Очистить выделение |

## YAML демо

Демо владеет своими `public/fixtures/entities.yaml` и `init_map.yaml`: кнопки в `index.html`
спавнят `mover`, `another_mover`, `truck`, `static_obstacle` и `base` по именам оттуда. Фикстуры библиотеки
в корневой `/fixtures` обслуживают Node-демо и тесты Rust и живут своей жизнью.

Правило движения то же, что в ядре: наличие `velocity` и есть разрешение двигаться, а
`base_move_speed` сверху делает юнита управляемым приказами. У `static_obstacle` нет ни того, ни
другого — его нельзя ни сдвинуть приказом, ни заставить дрейфовать.

У `truck` сверху `boardable: 4` — это и делает его машиной. В стартовой расстановке он стоит
вплотную к `mover` и заведомо далеко от `another_mover`: по **B** первый садится на первом же
тике, второму видно, как он идёт.
