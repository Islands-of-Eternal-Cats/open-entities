# Core API (WASM ↔ TypeScript)

Контракт между Rust/WASM-ядром и слоем визуализации.

**Первая установка:** если папки `wasm-bindings/pkg/` ещё нет, сначала соберите WASM:
`npm run build:wasm`, затем `npm install`.

## Общая схема

- **Ядро (WASM)** выполняется в **web worker**: симуляция, ECS-логика, состояние мира. Не знает о
  DOM и канвасе.
- **Визуализация (TS)** в главном потоке: рендер, ввод, UI. Общается с ядром через `postMessage`
  (см. `core/worker-types.ts`).

Граница — только данные и вызовы функций; никаких общих мутабельных структур.

## Как устроен обмен

Ядро отдаёт мир одним JSON: `Simulation.getWorldAsJson()`, схема версии 3. Воркер разбирает его и
превращает в плоские строки `EntitySnapshot`, с которыми работает визуализация. Строки без
`entity_type` (сущности, созданные не из шаблона) и без позиции в снапшот не попадают.

**Идентификатор.** Ядро адресует сущности парой `{index, generation}`. Визуализации нужен строковый
ключ — для `Map` спрайтов и для `data`-атрибутов в DOM, — поэтому пара упаковывается в
`"<index>:<generation>"`. Обе функции лежат в `core/types.ts`: `entityIdToKey` и `keyToEntityId`.
Пара переживает despawn корректно: индекс может быть переиспользован, но поколение будет другим, и
старый ключ на новую сущность не укажет.

**Время.** Приложение считает `dt` в секундах (из `requestAnimationFrame`), ядро принимает целые
миллисекунды и отвергает ноль. Конвертация — в воркере, одной строкой, с нижней границей в 1 мс.

## API главного потока (`core/wasm.ts`)

- **`initWasm()`** — создаёт воркер, **на главном потоке** качает `open_entities_wasm_bg.wasm`
  (с обходом кэша), `fixtures/entities.yaml` и `fixtures/init_map.yaml`, передаёт буфер и оба YAML
  воркеру. Воркер вызывает `init(wasm)`, `new Simulation()`, `loadTemplatesYaml`, `loadMapYaml`.
  Вызывать один раз до всего остального.
- **`isWasmReady()`** — `true` после успешного `initWasm()`.
- **`snapshot()`** — состояние мира без продвижения времени.
- **`tick(dtSeconds)`** — один шаг симуляции, резолвится снапшотом.
- **`spawnAt(typeName, x, y, faction?)`** и **`spawnRandomAt(typeName, faction?)`** — спавн по имени
  шаблона; резолвятся только что созданной сущностью.
- **`moveSelectedTo(entityIds, point)`** — приказ «идти в точку» для списка ключей из снапшота.
  Пустой список — ошибка.

## Что доступно в ядре, но ещё не проброшено наверх

`Simulation` умеет больше, чем использует демо: `orderStop(ids)`, `despawn(ids)`, `isAlive(id)`,
`mapBounds()`. Когда понадобится — добавляются по образцу `moveSelectedTo`: сообщение воркеру,
ветка в `ecs-worker.ts`, обёртка в `wasm.ts`.

| Путь | Назначение |
|------|------------|
| `src/core/wasm-types.d.ts` | Объявления типов модуля `open_entities_wasm`. |
| `src/core/types.ts` | Типы приложения, схема экспорта, упаковка id. |
| `src/core/worker-types.ts` | Типы сообщений main ↔ worker. |
| `src/core/ecs-worker.ts` | Воркер: `Simulation`, разбор JSON, обработка сообщений. |
| `src/core/wasm.ts` | Обёртка главного потока и очередь запросов. |

## Семантика ввода (selection + orders)

Правила слоя визуализации:

- Move order отправляется **только** при обычном клике по пустой земле (или по миникарте), когда
  есть активный `selection`.
- Любой модификатор (`Shift`/`Ctrl`/`Alt`/`Meta`) блокирует отправку приказа.
- `Shift+click` — только операции выбора, не приказ.
- Очистка выделения выполняется явно: `Esc`, кнопка UI, либо правый клик по канвасу.
- Клик по пустоте без модификаторов при активном выделении не очищает выделение, а трактуется как
  приказ движения.

| Сценарий | Ожидаемое действие |
|------|------------|
| Обычный клик по пустой земле при активном выделении | Отправить приказ движения |
| Shift/Ctrl/Alt/Meta + клик по пустоте | Приказ не отправлять |
| Клик по миникарте с модификаторами | Только навигация камеры |
| Esc / кнопка UI / правый клик | Очистить выделение |

## YAML демо

Демо владеет своими `public/fixtures/entities.yaml` и `init_map.yaml`: кнопки в `index.html`
спавнят `mover`, `another_mover`, `static_obstacle` и `base` по именам оттуда. Фикстуры библиотеки
в корневой `/fixtures` обслуживают Node-демо и тесты Rust и живут своей жизнью.

Правило движения то же, что в ядре: наличие `velocity` и есть разрешение двигаться, а
`base_move_speed` сверху делает юнита управляемым приказами. У `static_obstacle` нет ни того, ни
другого — его нельзя ни сдвинуть приказом, ни заставить дрейфовать.
